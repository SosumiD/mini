# Marketplace architecture

## Домены

- Users — покупатели и продавцы.
- Catalog — товары продавцов.
- Feed — выдача товаров пользователю.
- Orders — оформление и хранение заказов.
- Payments — платежи.
- Notifications — уведомления о статусах заказов.

## Сервисы

Каждый домен выделен в отдельный сервис.

- User Service владеет данными пользователей.
- Catalog Service владеет товарами.
- Feed Service формирует ленту.
- Order Service владеет заказами.
- Payment Service владеет платежами.
- Notification Service отправляет уведомления.

Общих баз данных между сервисами нет.

Синхронные запросы выполняются по HTTP. События изменения каталога и статусов заказов передаются асинхронно.

## Варианты архитектуры

### Вариант 1. Модульный монолит

Плюсы:
- проще запускать;
- проще разрабатывать;
- меньше инфраструктуры.

Минусы:
- сложнее независимо масштабировать части системы;
- сильнее связаны модули.

### Вариант 2. Микросервисы

Плюсы:
- независимое масштабирование;
- четкие границы ответственности и данных;
- сервисы можно развивать независимо.

Минусы:
- сложнее инфраструктура;
- сложнее взаимодействие между сервисами.

## Финальный вариант

Выбран вариант с отдельными сервисами по доменам. Он хорошо показывает границы ответственности, владение данными и взаимодействия, которые требуются в задании.

## C4

C4 Container диаграмма находится в `architecture/container.puml`.

## Реализованный сервис

Для задания реализован минимальный FastAPI-сервис только с health-check endpoint.

`GET /health`

Ответ:

```json
{"status":"ok"}
```

HTTP status: `200 OK`.

## Запуск

```bash
docker compose up --build
```

Проверка:

```bash
curl -i http://localhost:8000/health
```

Остановка:

```bash
docker compose down
```
